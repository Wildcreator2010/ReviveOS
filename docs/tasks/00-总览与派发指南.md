# ReviveOS 任务清单 · 总览与派发指南

> 版本：v1.0（2026-10-06）
> 交付边界：可直接上生产环境的完整系统（CLI + 后端 + 智能体 + 沙箱 + 胶囊 + Web 控制台 + 生产化 + Benchmark）
> 使用方式：你（人类）只做两件事——按依赖顺序派发工单、按验收命令验收。每条工单自包含，LLM 拿到即可开工。

---

## 1. 全局决策记录（已定死，LLM 不得更改；如与工单冲突以本节为准）

| 决策项 | 定论 |
|---|---|
| 仓库形态 | 单仓 monorepo，目录结构见 §3 |
| 平台自身运行时 | Python ≥ 3.11，包管理用 `uv`；Node ≥ 20 LTS，包管理用 `pnpm` |
| 被复生目标（Phase 1） | GitHub 公开仓库 + Python 2.7/3.x + Linux 容器 + pip/conda 依赖 |
| CLI 框架 | `typer` + `rich`（生产级，非一次性原型；与 Web 共享 `packages/core`） |
| 后端 | FastAPI + SQLAlchemy 2.x(async) + Alembic + Celery + Redis |
| 数据库 | PostgreSQL 16（含 pgvector 扩展）；对象存储 MinIO（S3 兼容） |
| 智能体编排 | LangGraph；状态持久化到 PostgreSQL |
| 模型接入 | 可插拔 Provider：`openai` / `anthropic` / `custom`（OpenAI 兼容端点，用户自带 base_url + api_key）。**代码中禁止出现任何真实密钥**，全部走环境变量 `REVIVE_LLM__*` |
| 沙箱 | Docker（docker-py），默认断网、非 root、CPU/内存/磁盘/超时四重限制；Windows 开发机走 Docker Desktop + WSL2 后端 |
| Web | Next.js 14 App Router + TypeScript strict + Tailwind CSS + shadcn/ui + TanStack Query；API 客户端由后端 OpenAPI 自动生成（`openapi-typescript` + zod） |
| 认证 | 邮箱+密码 JWT（access 15min / refresh 7d）+ API Key（长期，哈希存储，CLI/CI 用）；角色仅 `user`/`admin` |
| 事件流 | 任务过程事件 Redis Pub/Sub → SSE 端点推给前端与 CLI |
| 部署 | `docker-compose.prod.yml` 单机生产；全部服务化，无裸进程 |
| 可观测性 | structlog(JSON) + OpenTelemetry + Prometheus metrics；日志聚合 Loki + Grafana |
| 代码质量 | ruff（lint+format）、mypy --strict（Python 侧 packages/agents/cli）、ESLint + tsconfig strict TS；pre-commit；conventional commits |
| 测试 | pytest（单元+集成，集成层需 Docker）、Playwright（前端 E2E）、契约测试校验 schemas/ 一致性 |
| Git 约定 | 每条工单一个分支 `task/<工单ID>`，PR 标题 = 工单标题；合并前必须过 CI |

## 2. 工单格式（每条工单六段，验收必须是可执行命令）

```text
### <工单ID> <标题>
背景   —— 为什么做、与整体链路的关系（LLM 不需要读其他文档即可理解）
涉及文件 —— 精确到路径；新建文件列出完整路径
输入/输出契约 —— 函数签名/API 路由/JSON schema 引用（单一事实来源在 schemas/ 目录）
验收   —— 终端可执行的验证命令 + 期望输出；无法用命令验证的写明人工检查点
禁止   —— 本任务特有红线（全局红线见 §6）
依赖   —— 前置工单 ID（无则标「可立即派发」）
```

├── agents/                   # Python 包 `revive_agents`：LangGraph 图 + LLM Provider 抽象

## 4. 契约先行：四个核心 JSON Schema（T-INIT-02 一次性定稿，后续工单只读）

| 契约 | 用途 | 关键字段（详定义见 schemas/ 文件本身） |
|---|---|---|
| `revive-manifest.schema.json` | `.revive` 胶囊 manifest.json v1 | `format:"revive/v1"`, `source{repo,commit}`, `genome_ref`, `behavior{compatibility}`, `score{total,components}`, `patches[]`, `sbom_digest`, `provenance{evidence[],llm_traces[]}`, `status` 枚举: `alive/partial/dead` |
| `environment-genome.schema.json` | 考古产出的环境基因 | `python{version,confidence,evidence[]}`, `os{image,confidence,evidence[]}`, `dependencies[{name,version,source,confidence}]`, `cuda`, `system_libs[]`, `overall_confidence` |
| `job-event.schema.json` | 任务过程事件流（Redis/SSE/CLI 渲染共用） | `{id, job_id, project_id, ts, type, payload}`；`type` 枚举固定 15 种：`job.queued, archaeology.started, archaeology.evidence, env.inferred, sandbox.created, build.attempt, build.failed, repair.attempt, repair.applied, test.attempt, behavior.captured, behavior.compared, score.computed, capsule.created, job.succeeded/failed`（后两个互斥终态） |
| `resurrection-score.schema.json` | 复生评分 | 六分量与权重：runtime .20 / dependencies .20 / build .15 / tests .15 / behavior .20 / reproducibility .10；`total = Σ(component×weight)`，0–100 |

**关键路径**：`T-INIT-01/02` → `T-CORE-01..05`（考古与基因）→ `T-SB-01..04`（沙箱内构建闭环）→ `T-AG-02..05`（修复 Agent 环路）→ `T-CAP-01..03`（评分+胶囊）→ 其余全部可并行。

**端到端冒烟里程碑**（每过一个阶段必须现场演示的命令）：
- M1（P1 末）：`revive analyze https://github.com/<demo-old-python-project>` 打印出符合 genome schema 的推断结果
- M2（P2 末）：`revive run` 在沙箱内对目标项目完成 build→失败→修复→build 成功 一次完整环路
- M3（P3 末）：`revive resurrect <repo> -o out.revive` 产出可被 `revive verify out.revive` 通过的胶囊
- M4（P4 末）：Web 控制台粘贴 GitHub URL → 实时看到 16 类事件流 → 下载胶囊
- M5（P5 末）：`docker compose -f infra/compose/prod.docker-compose.yml up` 后全链路 + 鉴权 + 限流可用
- M6（P6–P7）：`revivebench run --suite pilot30` 输出对比表（数据必须真实产生，禁止填表）

## 6. 全局禁止事项（每张工单隐含继承）

1. 禁止把任何 API Key / 密码 / token 写入代码、配置样例、测试夹具（用 `REVIVE_LLM__API_KEY` 等环境变量与 `.env.example` 占位）。
2. 禁止跳过 schemas/ 直接手写 JSON 结构；字段增删必须先改 schema 再改实现（同一工单内完成）。
3. 禁止在控制面进程内直接执行用户代码——一切用户代码只允许在沙箱容器里运行。
4. 禁止引入未在 §1 决策表中的重型依赖（如 MongoDB/Kafka/Neo4j）；确有需要先在工单产出物里写明理由并留待人类批准。
5. 禁止在文档/测试数据/比赛材料中编造数字（含 Benchmark 结果、成功率、市场规模）。
6. 禁止破坏性 git 操作（force push、rebase 已推送分支）；禁止 `--no-verify`。
7. LLM 修复 Agent 的权限上限（写在代码常量并在 CI 校验）：`max_iterations=5, max_files_changed=10, max_lines_changed=300`，任何工单不得放宽。
8. 验收命令必须真实运行并贴出输出；「理论上可以通过」视为未完成。

## 8. 给派发者（人类）的三条提示

1. **一次只派一条工单给一个 LLM**；同一文件栈的多条工单串行，跨栈（有契约保护时）可并行。
2. 验收时优先跑工单的「验收」命令原样，其次跑 `make lint && make test`；两条都绿才合并。
3. 若 LLM 报告与契约冲突——契约赢，退回返工；若契约本身有缺陷，开一条 `T-FIX-契约` 小工单先改契约。
